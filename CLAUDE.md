# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`shortcutkit` builds, validates and signs Apple Shortcuts (`.shortcut`) files from TypeScript (Bun) and Python. The action catalogue and value encodings in `data/` were extracted from WorkflowKit and ActionKit (the private frameworks that are the Shortcuts engine) on a Mac, and both packages are generated from that data. macOS is required for `plutil` conversion, `shortcuts sign` (which additionally needs an iCloud login, so it cannot run on CI runners), and re-extraction; everything else is portable.

## Commands

```bash
bun install
bun test                      # all tests (test/shortcut.test.ts)
bun test -t "control flow"    # single test by name
bun run typecheck             # tsc --noEmit; also verifies the @ts-expect-error assertions in tests
bun run build                 # bun build src/index.ts → dist/index.js (Node ESM, JSON inlined) + tsc .d.ts; npm ships dist/ only
bun run demo out.shortcut     # builds, writes and signs a demo shortcut (macOS)

# Python package
cd python && python3 -m venv .venv && .venv/bin/pip install -e .
.venv/bin/python -m shortcutkit demo /tmp/Demo.shortcut

# Data pipeline (any Mac, no Xcode needed, ~10 s)
bun run extract               # regenerates data/, docs/, src/generated/actions.ts, python/src/shortcutkit/actions.py, provenance; also writes the local-only dumps. Needs Shortcuts.app to have run once (its ToolKit index)
bun run diff-data             # committed data vs working tree; recommends semver bump
bun run changelog             # same diff as a CHANGELOG section
```

CI (`.github/workflows/ci.yml`) runs typecheck, `bun test`, builds `dist/` and imports it from Node 20, installs the Python package, and writes an unsigned demo shortcut, all on `macos-latest`. It also runs `bun run verify` with `VERIFY_TRACE=1`, after recording a "denied" Contacts privacy answer in the runner's TCC.db (without one, Filter Contacts' sort-property state waits forever for a prompt). When the runner's Shortcuts build is older than `data/provenance.json`'s, keys its engine does not define or hides, built-in Find actions it lacks, and entity properties or filter row values the classes it builds do not have, are reported as version gaps rather than failures; on the extraction build or newer every miss fails. `VERIFY_ONLY=<regex>` limits the engine check to matching identifiers and `VERIFY_TRACE=calls` logs each engine call. Signing is not covered by CI: `shortcuts sign` fails with "you must be signed into iCloud" on GitHub runners.

Releases are published by `.github/workflows/release.yml` when a `v<major>.<minor>.<patch>` tag is pushed: it checks the tag against both manifests, runs the tests, builds `dist/` and the Python sdist and wheel on Ubuntu (nothing in the publish path needs macOS), and publishes to npm and PyPI through trusted publishing (OIDC, no stored tokens; both registries then show provenance). Both registries hold a Trusted Publisher entry for this repository, that file name and the `release` environment; a tag pushed by anyone else, or one that does not match the versions, fails before anything is built. `test/shortcut.test.ts` asserts that `package.json`, `python/pyproject.toml` and `__version__` agree.

## Architecture

**Data flows one way: engine → `data/` → generated code → library.**

1. `tools/extract-builtin-actions.sh` runs three JavaScript for Automation probes (`extract-builtin-actions.js`, `extract-parameter-encodings.js`, `extract-encoding-table.js`, each prefixed with `jxa-prelude.js`) under `osascript`. They `dlopen` ActionKit and WorkflowKit, ask `WFBundledActionProvider` for every definition, then serialize each parameter's state class. They are JXA rather than compiled code because ActionKit, which defines 53 of the built-in actions (Ask for Input, Show Alert, Count, URL, ...), asserts at load time that the host is an Apple platform binary, and a platform binary refuses to map non-platform code; osascript is a platform binary with no library validation. The prelude's `make()`/`sendObjects()` helpers call `objc_msgSend` on raw pointers where the JXA bridge cannot resolve a private initializer. Output: `data/builtin-actions.json` (definitions), `data/parameter-encodings.json` (parameter class → state class, plus per-action run-time parameter lists), `data/encoding-table.json` (exact serialized shapes), `data/provenance.json` (macOS/Shortcuts build that produced them).
   `tools/extract-encoding-table.js` also records `appIntentValueTypes`: the WorkflowKit parameter class the engine uses for each LinkMetadata value type (`-[LNValueType wf_parameterDefinitionWithParameterMetadata:]`, constructible without linkd), which types App Intent parameters. `tools/dump-toolkit-registry.py` then reads the Shortcuts app's own action index (`~/Library/Shortcuts/ToolKit/Tools-prod.*.sqlite`, the only readable copy of linkd's App Intents registry; linkd itself needs the `com.apple.linkd.registry` entitlement) and writes `data/apple-app-intents.json` (Apple apps' App Intents: exact identifiers, owning app, typed parameters, enum cases, Apple's snake_case keys) plus local-only `toolkit-registry.json`/`toolkit-names.json` (plus a copy stamped with the OS build, since the app rebuilds its index on every update); `tools/annotate-builtin-actions.py` fills `Name`, enumeration `Items`, and parameter `Label`/`Description` (the hover docs on `ParamTypes` keys) from the registry and `Output.OutputName` from the engine's action objects (`actionOutputNames` in `parameter-encodings.json`, "Provided Input" for Ask for Input) for what the definitions leave out (ActionKit's built-ins declare parameters in code), each marked with a `*Source` key; enumeration entries only for keys the run-time walk reports.
   `dump-toolkit-registry.py --entities` also exports the index's entity types (`EntityProperties`, `PredicateTemplates`: protobuf blobs that ToolKit's own `CCToolKitToolType*` classes decode), and `tools/extract-entities.js` has WorkflowKit build each entity's content item class from them without linkd (`entityContentClass()` in the prelude, via `-[LNEntityMetadata wf_contentItemClassWithEntityValueType:…]`), then records per property the operators, the row value kind (from its editing parameter), the calendar units (`timeUnits`) and whether a property aggrandizement finds it, loading a sample row per operator through a Find action on the class. Output: `data/apple-entities.json`. Built-in Find actions' operators are computed in Swift with no ObjC entry point, so this route types only App Intents Find actions; the generator now takes its Find filters from the engine data below and falls back to this file for an entity the host did not build.
   `bun run extract-filters` (`tools/extract-engine-filters.sh`, optional, about 25 s: needs the Xcode Command Line Tools and the loader shortcut from `tools/linkd` imported into Shortcuts) reads those Swift rules anyway. `tools/linkd/run-payload.sh` runs a script inside `ShortcutsMacHelper`, the one process we can drive that linkd answers (it has the `com.apple.linkd.registry` entitlement), through the loader shortcut `SK <sha256 of loader.js>`; `archive-metadata.js` saves linkd's metadata to `~/.shortcutkit-dev/linkd/` (7 s). `tools/engine-host` (`skhost`, run under lldb by `run.sh`) loads ActionKit past its platform-binary assertion, serves those archives in place of linkd, and calls `RowTemplateFindFilterParameterState`'s private Swift functions; `tools/extract-engine-filters.js` runs in it twice, because the engine registers one content item class per type name: mode `index` builds the entities as `extract-entities.js` does and writes `data/engine-filters.json` (every content item class's subject type; per property the engine's operators, bounded operators, Swift value type, value class and static `items`, for the 30 built-in Find/Filter classes and all 434 entities; `rowValues`: a sample of every row value form read back through the engine and through its run-time row model, `WFRowTemplateValue` + `WFContentPredicateForRowTemplateValue`, which gives the `ByteCountUnit` codes and the `Email`/`Phone`/`String` key per value class); mode `linkd` builds them from linkd's own metadata and query, as the app does, and writes `data/linkd-properties.json` (the same rules for those classes, enumeration `cases` per property, what each property reference yields, and the type's queries: where linkd has several, `dump-toolkit-registry.py` reads the one the index's parameters embed, `queries`, and the file holds the class built with each under `byQuery`). It also runs `tools/linkd/action-metadata.js` and saves linkd's per-action availability and visibility as `data/linkd-actions.json` (committed); `dump-toolkit-registry.py` reads it (in `bun run extract`, or `--linkd-actions` when given another data dir) and leaves out every intent linkd marks not discoverable, the Siri-only intents the app refuses to import (135 on macOS 27; warns and keeps them when the file is absent). The payloads' bundle list comes from the full local index (`engine-filter-args.py bundles`), never from the filtered catalogue. `--check` re-resolves every property inside the helper over XPC to the real linkd (`resolve-properties.js`, ~10 min, resumable) and `tools/compare-linkd-properties.py` requires the two to agree. `generate-action-catalog.py` types `where()` from both files (`engine_rows`: built-in Find actions from `builtin`, App Intents Find actions from the linkd-built `filters`; row kinds text/email/phone/number/date/duration/fileSize/enumeration/enumCase/contactHandle), and `bun run verify` loads the rows through the engine actions and, when the host is built, through the linkd-built classes (see `docs/extraction.md` for what is still open). Never reuse a loader shortcut's name for a changed script; a hung run needs `killall siriactionsd` (`run-payload.sh` does this itself when the payload's progress file says it finished).
2. `tools/generate-action-catalog.py` reads those and writes **both** `src/generated/actions.ts` and `python/src/shortcutkit/actions.py`, plus `src/generated/params.ts` (a `<Key>Params` alias per action), and `src/generated/entities.ts`/`python/src/shortcutkit/entities.py` (`FILTERS`, `ENTITY_PROPERTIES`, `FILTER_OPERATORS`, `CALENDAR_UNITS`, and the `FilterRows` tuple types that type `WFContentItemFilter` on those Find actions). Each `ParamTypes` key carries the editor's label and description as JSDoc (`doc_text`), so editors show them; keys without either stay bare rather than get invented text. `ACTIONS` entries carry `outputTypes`. App Intents entries carry a `descriptor` that `action()` writes as `AppIntentDescriptor`; their keys are the app's `pythonName`, with variants (assistant twins, widget configurations, migrated `is.workflow.` identifiers) falling back to the sanitized identifier (`dedupe_keys`). Never hand-edit either; change the generator or the data and re-run. The state-class → value-kind mapping (`STATE_KIND`, `KIND_TS`) and the `LEGACY` keys for If/Choose-from-Menu live in this script.
3. `src/index.ts` is the whole runtime (control flow: `if`/`otherwise`/`endIf`, `repeatEach`, `repeatCount`, `chooseFromMenu`/`menuItem`/`endMenu`) (Node and Bun; it uses only `node:` builtins, and relative imports carry `.js` extensions so the emitted `.d.ts` resolve under NodeNext): `Shortcut` class, value helpers (`ref`, `variable`, `text`, `property`, `coerce`, `dictionary`, `appIntent`, `where`/`whereAny`, …), control flow, `toPlist`/`write`/`sign`. `src/values.ts` defines the value-shape types the generator references (`BoolValue`, `TextValue`, `EnumValue<…>`, …). `src/definitions.ts` types the raw JSON; `src/provenance.ts` exports `data/provenance.json`; `src/plist.ts` is a minimal XML plist writer; `src/cli.ts` is the `demo` command.
   `tools/verify-encodings.js` round-trips every value form the library writes through each state class's own parser (`data/encoding-roundtrips.json`) and fails the pipeline if a kind's form is rejected. `bun run verify` (`test/verify/run.sh`; CI runs it too; on a runner older than the data it reports version gaps instead of failing) is the full check: `test/verify/fixture.ts` and `fixture.py` drive both packages over every action, key and value form (plain sample, token string, every reference helper, raw forms the library refuses) plus whole shortcuts through every block helper; `parity.py` diffs the two; `tools/verify-library-output.js` loads every case through the engine's action objects (`-copyWithSerializedParameters:` then `-parameterStateForKey:`) and whole shortcuts through `WFWorkflowFile`, and every `where()` filter and `property()` reference through the entity's content item class (rows must serialize back as written), failing on anything not read and on any refused form the engine does read. Run it after changing `action()`, a helper, the generator or the probes. Never fix a verifier failure by special-casing the failing key: find the rule in the engine (as with `reads`) and put it in the data.
   `extract-parameter-encodings.js` also records per key `reads` (the reference kinds the engine produced a state for when each was loaded through the action), `readsPlain` (whether a plain sample was read: the key's default, else its first possible state), `variableTypes` (the editor's picker list, narrower than `reads` for many enumerations) and `unavailableActions` (definitions the engine loads as missing; `Unavailable` in the definitions).
4. `python/src/shortcutkit/__init__.py` mirrors `src/index.ts` (same helpers, snake_case, `if_`/`end_if`, `property_`, `where_any`) with run-time kind checks (`PARAM_KINDS`) standing in for TypeScript's compile-time `ParamTypes`. The extract script copies `builtin-actions.json` and `provenance.json` into `python/src/shortcutkit/data/`.

**Typing model.** `Shortcut.action(id, params)` is generic over the identifier: a built-in `ActionId` gets `Partial<ParamTypes[id] & MetaParams>`, anything else (App Intents from installed apps) gets `Record<string, Value>`. A plain value type is unioned with `Attachment` where the engine reads a reference; `Attachment<T>` is generic over the variable type (`ref()` returns `Attachment<"ActionOutput">`, `ask()` an `AskAttachment`), and a key that reads fewer than all eight kinds gets `Attachment<…>` naming them, from `reads` in the data (`PARAM_VARIABLE_TYPES` carries the same table for run time in both packages; block helpers such as `repeatEach()` take their parameter type from `ParamTypes`). Enum choices use `Loose<T>` so unknown strings still compile. Run-time validation in `action()` checks identifiers starting with `is.workflow.` and unknown parameter keys against the definitions, using `META_KEYS` and `LEGACY_KEYS` for keys the definitions don't list.

**Encoding facts to preserve.** References are `WFTextTokenAttachment`; `text()` interleaves strings and attachments with U+FFFC placeholders keyed by `{offset, 1}` ranges (offset in UTF-16 code units, as NSRange counts; verified against WorkflowKit with emoji). Variable-picker parameters take the bare attachment; only the If condition's subject (`WFInput` on `is.workflow.actions.conditional`) is wrapped as `{Type: "Variable", Variable: …}` (`subject()`; `picker()` is a deprecated alias of it). `action()` wraps bare references for `text` and `subject` kinds, and encodes `where()` rows: `String` (token string, never a bare reference), `Number`, `Date` (a plist date, never a string), `ContactHandle` (wrapped in `WFTokenStringParameterState`, a plain string when it holds no reference), `Number`+`Unit` (NSCalendarUnit) for in the last/next; prefix 1 = all. Dictionary items (`dictionary()`, and `action()` on a plain object for a `dictionary` key): `WFItemType` 0 text (token string), 1 dictionary (`WFValue` wrapped once more: `{WFSerializationType: WFDictionaryFieldValue, Value: <the dictionary>}`), 2 array (`WFArrayParameterState`; plain text items are bare strings, other items `{WFItemType, WFValue}` with no key), 3 number (a token string, never a bare number), 4 boolean (`WFNumberSubstitutableState`); the engine's parser raises on any other code (`dictionaryItems` in `data/encoding-table.json` holds what it writes back). Coercions (`coerce()`) are `WFCoercionVariableAggrandizement`; the parser takes any class name, so the library checks against `CONTENT_ITEM_CLASSES` (`+[WFContentItem allSupportedItemClasses]`, `contentItemClasses` in the encoding table, the editor's "Type" menu). `appIntent()` composes a third-party identifier as bundle identifier + intent name, which every catalogue entry follows. Control-flow blocks share a `GroupingIdentifier` with `WFControlFlowMode` 0 (open), 1 (middle branch), 2 (close). `docs/shortcut-file-format.md` is the full format reference; `docs/extraction.md` records how each fact was obtained and what is still approximate (every operator code is named by the engine: `filterOperators` in `data/encoding-table.json`).

## Conventions

- Keep the TypeScript and Python packages in feature parity; a change to `src/index.ts` usually needs the same change in `python/src/shortcutkit/__init__.py`, and tests in `test/shortcut.test.ts` assert exact counts (449 built-in definitions, 1714 catalogue entries, 1265 with descriptors, 150 Find filters, 752 entity properties, 135 intents linkd marks not discoverable and none of them in the catalogue) that change only with a data refresh; `.github/workflows/ci.yml` asserts the catalogue and descriptor counts for the Python package too.
- Data refreshes follow semver for the whole repo: additions are minor, removals or class changes are major. Update `CHANGELOG.md` with `bun run changelog` output and bump both `package.json` and `python/pyproject.toml`.
- `data/gallery-workflows.json`, `data/app-provided-actions.json` and `data/builtin-action-identifiers.txt` are local-only dumps (gitignored); do not rely on them in committed code.
- Other tools: `tools/dump-gallery.py`, `tools/dump-appintents-actions.py`, `tools/dump-library-encodings.py` (read-only inspection of Apple's gallery, installed apps' App Intents, and the local Shortcuts library), `tools/fetch-apple-docs.py` (Apple docs as markdown), `tools/diff-data.py` (semver recommendation for a data refresh), `tools/audit-catalogue-coverage.py` (every action the editor shows on this Mac that the catalogue lacks, with the rule that left it out; fails on one no rule explains; with linkd's action metadata saved it also lists the catalogue entries the app refuses to import), `tools/linkd/action-metadata.js` (a `run-payload.sh` payload: linkd's per-platform availability and visibility of each Apple App Intents action, to `~/.shortcutkit-dev/linkd/actions.json`). One-off probes: `tools/jxa-probe.sh probe.js` runs a `run(argv)` script against the engine under osascript with the prelude prepended; `tools/engine-host/syms.sh '<regex>'` lists WorkflowKit's matching symbols from a one-off lldb session on the host.
- Hidden actions: a built-in the editor hides still imports and runs; an App Intents action linkd marks not discoverable (`assistantOnly`) is refused by the app's import sheet ("features not supported on this device"), although the engine loads it. The 135 such Siri-only intents on macOS 27 (Reminders' Open List, Books' Play Most Recent Audiobook, ...) are out of the catalogue since 2.0.0, by linkd's flag: the index's `visibilityFlags` 2 matches them only among tools that have linkd action metadata, while synthesized entity tools and flow tools share the value and do import. The four Focus-filter intents carry a configuration protocol but the editor lists them, so they are in. Details are in `docs/extraction.md` under "What the editor shows that the catalogue does not".
- The JXA probes call private API by selector name; if extraction breaks after a macOS update, re-dump the method lists of `WFBundledActionProvider`, `WFActionDefinition` and `WFParameterSummary` (the prelude's `methodNames()` does this from JXA) and adjust (see `docs/extraction.md`).
